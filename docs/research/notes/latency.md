# Latency techniques for a long structured-JSON report pipeline (open-weight models, OpenAI-compatible vLLM API on GWDG SAIA)

Context supplied by the requester (not independently verified): extraction ~4 s; one monolithic draft call, ~1,600 schema-constrained JSON output tokens, Qwen3.5-397B-A17B, ~25 s; critic with Gemma 4 31B ~8 s; whole-report repair ~30 s on most enquiries; total 40-72 s; deterministic stages < 0.1 s; SAIA limits 30 requests/min and 200 requests/hour.
Research date: 2026-10-17. Evidence-quality tags used below: [P] = primary paper/official doc, [V] = vendor/engineering blog with own measurements, [S] = secondary/aggregator/community, [E] = my own arithmetic or estimate (always in Inferences).
Two framing observations from the findings: (1) 1,600 tokens / 25 s is about 64 tok/s end-to-end, which matches published non-reasoning decode speeds for Qwen3.5-397B (see section 4), so the draft stage is almost entirely decode-bound; (2) the 200 requests/hour cap, not the 30/min cap, is likely the binding constraint on any fan-out design (see section 8).

## 1. Skeleton-of-Thought (SoT) and parallel section generation

### Takeaway
SoT (ICLR 2024) reports up to 2.39x speed-up across 12 LLMs, with a quality profile that is good for list-like/knowledge answers and poor for math/coding/writing, and it explicitly ignores dependencies between points and hurts coherence. Because your skeleton comes from a deterministic engine, the skeleton-generation step and the "is this question suitable" router disappear, so the achievable speed-up is bounded mainly by your longest section plus TTFT, with the main quality risk being cross-section inconsistency.

### Cited Findings
- SoT first generates an answer skeleton, then fills each point via parallel API calls or batched decoding; abstract claims considerable speed-ups across 12 LLMs and possible quality gains on several question categories [P] — [arXiv 2307.15337](https://arxiv.org/abs/2307.15337)
- Concrete numbers: Claude 22 s to 12 s (1.83x) and Vicuna-33B V1.3 43 s to 16 s (2.69x) on an example question; "up to 2.39x" across 12 models and ">2x" on 8 of 12; 1.89x-2.33x speed-up on the five categories where SoT works well (knowledge, generic, common-sense, roleplay, counterfactual) [P] — [SoT paper, arXiv HTML v3](https://arxiv.org/html/2307.15337v3)
- The earlier preprint abstract says 11 LLMs, the ICLR 2024 version says 12 LLMs (version discrepancy, same method) [P/S] — [Microsoft Research summary](https://www.microsoft.com/en-us/research/publication/skeleton-of-thought-large-language-models-can-do-parallel-decoding/); [ICLR 2024 listing](https://mlanthology.org/iclr/2024/ning2024iclr-skeletonofthought)
- Quality (GPT-4 judged, no human eval): SoT strictly better in 45.8% of cases (FastChat metric) and 29.5% (LLMZoo); not worse than normal generation in about 60% of cases. Relatively good on generic/common-sense/knowledge/roleplay/counterfactual; relatively poor on writing, fermi, math, coding. SoT improves diversity and relevance but hurts immersion and coherence [P] — [SoT paper HTML v3](https://arxiv.org/html/2307.15337v3)
- Stated limitations: unsuited to step-by-step reasoning; "currently ignores the dependencies between points"; for API models it raises prefill tokens; under saturated concurrent load the extra computation can reduce serving throughput; speed-up is prompt/model/question dependent and less predictable than system-level techniques [P] — [SoT paper HTML v3](https://arxiv.org/html/2307.15337v3)
- SoT-R: a router (GPT-4 prompting, or a ~120M-parameter fine-tuned RoBERTa trained on LIMA) sends unsuitable questions to normal decoding, significantly improving quality on coding/math/writing/fermi questions while retaining speed-ups above 1x for most models (lower than plain SoT) [P] — [SoT paper HTML v3](https://arxiv.org/html/2307.15337v3)
- Successor "Skeleton Graph Decoding" (arXiv 2402.12280, listed as "Plato"): asks the model for dependencies and difficulty estimates; dependent sub-problems pass information, independent ones run in parallel, difficulty picks model size; reports 1.69x speed-up with quality up to 51% better than standard generation and SoT; its authors state parallel methods like SoT "often suffer from reduced response quality" [P abstract via search] — [Plato / SGD, arXiv 2402.12280](https://arxiv.org/pdf/2402.12280)
- APAR (2024) fine-tunes models so they emit hierarchical structures and plan their own parallel generation: up to 2x speed-up alone, up to 4x combined with speculative decoding; 20-35% latency reduction and 20-70% throughput gain in high-throughput serving. Requires fine-tuned model, so not usable on SAIA [P abstract via search] — [APAR, arXiv 2401.06761](https://arxiv.org/abs/2401.06761)
- OpenAI's latency guide lists "parallelize" (run independent steps concurrently) and "make fewer requests" (combine sequential steps) as separate principles, and notes output generation is usually the slowest step, so cutting output tokens by ~50% cuts latency by ~50%, whereas cutting input tokens by 50% improves latency only ~1-5% [V] — [OpenAI latency optimization guide](https://developers.openai.com/api/docs/guides/latency-optimization)
- Typical time-to-first-token for large hosted models on a 10k-token prompt is 1.2-2.2 s (Qwen3.5-397B non-reasoning across providers), so each parallel section pays a fixed ~1-2 s TTFT [S/V, Artificial Analysis snapshot, undated, 72-h median] — [Artificial Analysis, Qwen3.5 397B providers](https://artificialanalysis.ai/models/qwen3-5-397b-a17b-non-reasoning/providers)

### Inferences
- [E] With a deterministic skeleton, there is no "skeleton stage" (SoT's first sequential call) and no suitability router needed: you already know the section list and can decide statically which sections are independent. That removes SoT's two overheads, so the realised speed-up should be closer to N-way (N sections) than the paper's 2.0-2.4x, limited by the longest section + TTFT. Rough arithmetic: 1,600 tokens in 4 sections of ~400 tokens at ~60 tok/s is 6-7 s decode + 1-2 s TTFT = 8-9 s; allow uneven sections (longest 500-600 tokens) so 9-12 s versus 25 s, i.e. about 2-3x on the draft stage. This is an estimate, not a measured result.
- [E] SoT's measured quality loss (coherence, ignored dependencies) maps directly onto the risk of per-section calls: contradictory statements across sections, repeated content, inconsistent terminology. The mitigation is structural: give every section call the same shared "report state" (all deterministic facts, rule verdicts, retrieved evidence, section list and one-line intent for the other sections) and run a cheap deterministic cross-section check (shared identifiers, numeric consistency) after merge. Sections that depend on other sections' conclusions (e.g. an executive summary) should run last or be generated from the section outputs (a second, short, sequential call), which is the SGD idea (dependent sub-problems get context).
- [E] Prefill is duplicated N times (SoT limitation), but per OpenAI's rule of thumb input tokens have a small latency effect; it matters mostly for the 200/hour request budget, not for wall-clock.
- [E] Sections that are largely restatements of deterministic facts (tables, parameter lists, IDs) should not be LLM-generated at all; this is the highest-yield form of "generate fewer tokens".

### Gaps
- No published measurement of SoT-style fan-out for JSON-schema report generation with known skeleton; the 2.39x figure is from open-ended QA (Vicuna-80/WizardLM style), not structured reports.
- No data on how SAIA's gateway schedules concurrent requests (queueing/serialisation could erase parallel gains); must be measured with N concurrent calls.
- No evidence found on quality of independently generated scientific report sections vs monolithic generation.

## 2. Streaming structured output: partial JSON, per-section streaming, TTFT vs total time

### Takeaway
Streaming does not shorten total time but turns a 25-70 s blank wait into first content in about 1-2 s (TTFT of the first call); the robust pattern is per-section streaming (each section is its own call or its own JSON line) rather than parsing one long partial JSON object. SAIA supports `stream=True`.

### Cited Findings
- SAIA's OpenAI-compatible API supports streaming (`stream=True`, `chunk.choices[0].delta.content`); base URL chat-ai.academiccloud.de/v1; endpoints include /chat/completions and /completions. The page does not mention structured output/JSON schema support [P] — [GWDG SAIA docs](https://docs.hpc.gwdg.de/services/ai-services/saia/index.html)
- OpenAI: streaming is "the most effective technique" for making users wait less, reducing perceived waiting to about a second or less; also recommends chunking, showing progress through steps, and loading states [V] — [OpenAI latency optimization guide](https://developers.openai.com/api/docs/guides/latency-optimization)
- Anthropic's latency guide likewise lists streaming (process output as it arrives to update the UI) alongside model choice and shorter outputs [V] — [Anthropic, Reducing latency](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-latency)
- UX thresholds: ~1 s keeps flow of thought; ~10 s is the attention limit; beyond 10 s show a progress indicator with expected duration, and if total work is unknown show running progress in absolute terms such as names of items processed [P/V] — [Nielsen Norman Group, Response Times](https://www.nngroup.com/articles/response-times-3-important-limits/)
- Partial JSON is syntactically invalid at every intermediate step, so `JSON.parse` fails until the end; tolerant parsers (partial-json, best-effort-json-parser) return a structure from truncated input; field-level emission (once a field's type is fixed) is recommended; Vercel AI SDK exposes `partialObjectStream`/`elementStream` for arrays of complete items [S] — [search-result synthesis (Medium/tianpan.co/HN)](https://nitishagar.medium.com/streaming-structured-data-from-llms-is-harder-than-you-think-6f2ee976fe5f); [AI SDK streamObject reference](https://ai-sdk.dev/v4/docs/reference/ai-sdk-core/stream-object)
- Reported user issue: with a schema containing one large string field, streamObject chunks arrived in a burst only after generation finished (unconfirmed user report) [S] — [Vercel community thread](https://community.vercel.com/t/streamobject-not-truly-streaming-all-chunks-arrive-nearly-instantly/23972)
- Mid-stream failures cannot be retried transparently, so partial-result handling must be designed in [S] — [LLM Output Streaming: The Edge Cases That Bite](https://www.orzed.com/insights/llm-output-streaming-the-edge-cases-that-bite)

### Inferences
- [E] Three tiers of "something useful within seconds": (a) t < 0.5 s: render the deterministic output (rule verdicts, retrieved evidence, section scaffold with headings) with no LLM; (b) t ~ 5-7 s: first LLM section text begins streaming; (c) t ~ 15-25 s: all sections complete and checked. This satisfies the NN/g 10 s attention limit with visible progress at every step.
- [E] Prefer one streamed call per section with the section body as plain text/markdown plus a tiny JSON envelope (or NDJSON, one complete JSON object per line) over streaming one 1,600-token JSON object: you avoid partial-JSON parsing, avoid the "large string field arrives in a burst" failure, and a section can be shown, validated and repaired independently. Server-side grammar constraints still apply per call.
- [E] Streaming makes unverified text visible before the critic runs. For a grounded-science product, label streamed text "drafting/unchecked" and promote to "checked" after deterministic validators (and the critic, if run) pass; never show an unchecked numeric claim as final.
- [E] Total latency is unchanged by streaming, so streaming is a perception tool and should be combined with the throughput techniques (parallel sections, fewer tokens, targeted repair).

### Gaps
- Not verified whether SAIA's gateway buffers or flushes SSE chunks immediately for the Qwen3.5-397B route (needs a measurement of first-chunk latency).
- No primary benchmark of partial-JSON parsing libraries; the cited sources are community/blog level.

## 3. Constrained decoding cost/benefit (XGrammar, llguidance, outlines) and "let it speak first, then format"

### Takeaway
Modern backends (XGrammar, llguidance/Guidance) add negligible per-token overhead and can even speed up output through fast-forwarding deterministic tokens; Outlines is the slow one (seconds of compile time). The quality literature is contested: "Let Me Speak Freely?" found large JSON-mode reasoning losses, a dottxt rebuttal found these were prompt/parser artifacts, and later work (JSONSchemaBench, "The Format Tax") suggests the loss is mainly caused by format-requesting prompts and by answer-before-reasoning field order, not by the grammar mask itself. For a report-writing task, structure is cheap; keep reasoning/evidence fields before conclusion fields.

### Cited Findings
- vLLM docs: structured outputs use `xgrammar` or `guidance` as backends; enabled by default in the OpenAI-compatible server; default backend `auto`; selected server-side with `--structured-outputs-config.backend`; schema is passed through `response_format` (`json_schema`) or `extra_body={"structured_outputs": {...}}`; docs advise including the schema and field guidance in the prompt, which "can improve the results notably" [P] — [vLLM structured outputs](https://docs.vllm.ai/en/latest/features/structured_outputs/)
- XGrammar paper: under 40 microseconds per token mask for JSON Schema/CFG(JSON), under 200 microseconds for XML/Python DSL; up to 3x faster on JSON Schema and over 100x on CFG vs best baseline; mask generation runs on CPU overlapped with GPU. In MLC-LLM, time per output token was 6.2 ms without vs 6.3 ms with XGrammar for JSON Schema at batch 1, and 9.0 vs 9.2 ms at batch 16 (i.e. about 1-2% overhead). Function-calling accuracy 62% to 100% and XML code generation 80% to 100% with constraints [P] — [XGrammar, arXiv 2411.15100v3](https://arxiv.org/html/2411.15100v3)
- JSONSchemaBench (Geng et al., 2025; Llama-3.1-8B, mostly llama.cpp/HF backends, NOT vLLM): Guidance had lowest per-token latency (about 6-10 ms vs 15-17 ms for unconstrained LM-only run) and fast-forwarding of deterministic tokens roughly halved total generation time on GlaiveAI schemas (0.50 s vs 1.08 s); Outlines had compile times of about 3.5-8 s and 30-47 ms/token; XGrammar compile 0.1-0.3 s (overlapped with prefill) but 65-67 ms/token on the HF backend vs 36-44 ms for Guidance on the same backend; Guidance had highest schema coverage and fewest failures; XGrammar had the most under-constrained (too permissive) failures; Outlines timed out on features like minItems/maxItems/enum [P] — [JSONSchemaBench, arXiv 2501.10868v2](https://arxiv.org/html/2501.10868v2)
- JSONSchemaBench quality (Table 8): constrained methods were at or above unconstrained on Last Letters, Shuffle Objects and GSM8K (e.g. GSM8K LM-only 80.1%, XGrammar 83.7%, Guidance 83.8%, Outlines 81.6%, Llamacpp 82.4%); constraints did not hurt and modestly helped [P] — [JSONSchemaBench](https://arxiv.org/html/2501.10868v2)
- WGrammar paper (2025) reports XGrammar's TTFT overhead of roughly 117-2,748 ms across its datasets vs unconstrained TTFT of 18-526 ms, claiming a 250x TTFT-overhead reduction with its own method (figures from search-result summary, not verified in full text) [S/P] — [WGrammar, arXiv 2507.16768](https://arxiv.org/pdf/2507.16768)
- A third-party guide estimates XGrammar's one-time compile at 20-50 ms with caching on repeated schemas; no benchmark shown [S, unverified] — [Spheron blog](https://www.spheron.network/blog/structured-output-function-calling-inference-guide/)
- "Let Me Speak Freely?" (EMNLP 2024 Industry): JSON-mode/schema constraints reduced reasoning accuracy, e.g. GSM8K text vs JSON: GPT-3.5 76.6 vs 49.25, Claude 3 Haiku 86.51 vs 23.44, LLaMA-3-8B 74.73 vs 48.90; classification tasks often improved under JSON (DDXPlus: GPT-3.5 44.07 to 55.51); all GPT-3.5 JSON responses on Last Letter put "answer" before "reason"; the paper itself has internal inconsistencies (e.g. GPT-3.5 GSM8K JSON 49.25 in Table 6 vs 29.87 in Table 8), only five main models and nine prompt variants, and an LLM-based answer parser; suggests looser format restrictions or NL-to-format conversion for reasoning-heavy tasks, and says LLM reformatting of parse failures is cheap [P] — [arXiv 2408.02442](https://arxiv.org/html/2408.02442v1)
- dottxt rebuttal "Say What You Mean": inconsistent NL vs structured prompts, JSON-mode prompt never mentioned JSON or a schema, Claude-3-Haiku parser scored 0.57 vs 0.61 for a flexible regex; re-run gives structured >= unstructured: GSM8K 0.77 vs 0.78, Last Letter 0.73 vs 0.77, Shuffle Object 0.41 vs 0.44. Note the author is a structured-generation vendor (conflict of interest) [V] — [dottxt blog](https://blog.dottxt.ai/say-what-you-mean.html)
- "The Format Tax" (arXiv 2604.03616, preprint under review): across six open-weight and four API models and four formats (JSON, XML, LaTeX, Markdown), format-requesting instructions alone cause most of the accuracy loss, before any decoder constraint; decoupling reasoning from formatting (two-pass reformat, or extended thinking inside one generation) recovers most of it; recent closed-weight models show little to no tax [P preprint] — [arXiv 2604.03616](https://arxiv.org/abs/2604.03616)
- Schema-aware reasoning helps JSON generation accuracy by up to 16% ("Thoughts of Structure", SchemaBench) [P via search] — [arXiv 2502.18878](https://arxiv.org/pdf/2502.18878)
- vLLM docs say structured outputs can be combined with a reasoning parser (response splits into `reasoning` and `content`), but for some models structured output may be disabled unless reasoning is parsed (flag `enable_in_reasoning`); the page does not specify exactly when the grammar starts to apply relative to the end of reasoning [P] — [vLLM structured outputs](https://docs.vllm.ai/en/latest/features/structured_outputs/)

### Inferences
- [E] Per-token overhead of XGrammar/llguidance in vLLM is likely a low single-digit percent; the real cost risks are (a) first-request grammar compilation for complex schemas (tens of ms to ~seconds depending on backend and schema; unverified for SAIA) and (b) schemas using minItems/maxItems/large enums/$ref recursion that some backends handle badly. Mitigation: keep per-section schemas small and static (compiled once, cached), avoid exotic JSON-schema keywords, test each section schema against SAIA once at startup (warm-up).
- [E] Splitting the report into per-section schemas makes each grammar smaller, which tends to reduce compile time and mask size, and makes enum constraints practical (e.g. cited evidence IDs restricted to retrieved IDs), turning some critic findings (fabricated citation IDs) into impossible states.
- [E] The "let it speak first" evidence supports ordering rather than a second LLM pass: in each section schema put `evidence`/`rationale` fields before `verdict`/`conclusion` fields (the failure mode in Tam et al. was answer-before-reason). A separate NL-then-format pass would add a full extra call and seconds, so it should only be used for the few sections that need real multi-step reasoning.
- [E] The client generally cannot choose the guided-decoding backend on SAIA (server flag); the client controls only schema design, prompt wording and field order.

### Gaps
- No vLLM-specific per-token overhead number for large MoE models (Qwen3.5-397B) with XGrammar vs llguidance; the best numbers are from MLC-LLM (XGrammar paper) and llama.cpp/HF (JSONSchemaBench).
- Not known which backend/version SAIA runs, nor whether it supports `response_format: json_schema` for each hosted model (SAIA docs silent; requester says the draft is already schema-constrained, so presumably yes).
- Interaction of grammar masks with speculative decoding (MTP/EAGLE) in vLLM not documented in the sources found.
- No study found that measures quality of constrained vs unconstrained decoding for long scientific prose fields inside JSON.

## 4. Output-token reduction, decode speeds (large MoE vs mid-size), model routing and cascades

### Takeaway
Generation is decode-bound, so the highest-leverage levers are fewer output tokens and splitting work across calls; published per-provider decode speeds for Qwen3.5-397B-A17B are roughly 13-141 tok/s (median-ish ~56), overlapping heavily with 3B-active and 31B models, so model-size routing buys 0-2x depending on provider and must be measured on SAIA. RouteLLM/FrugalGPT evidence is about cost on general benchmarks, not latency on domain reports.

### Cited Findings
- OpenAI: cutting ~50% of output tokens cuts ~50% of latency; cutting 50% of input tokens only ~1-5%; ways to cut output: ask for brevity, minimise structured-output syntax (shorter keys, fewer named arguments), move explanations out of the structured output, use `max_tokens`/stop tokens; going too far (single-character keys) can hurt quality; hard-code highly constrained outputs and "don't default to an LLM" [V] — [OpenAI latency optimization guide](https://developers.openai.com/api/docs/guides/latency-optimization)
- Qwen3.5-397B-A17B: 397B total / 17B active, 60 layers hybrid Gated DeltaNet + gated attention, 512 experts with 10 routed + 1 shared active per token; trained with multi-step MTP [P] — [Qwen3.5-397B-A17B model card](https://huggingface.co/Qwen/Qwen3.5-397B-A17B)
- Artificial Analysis, Qwen3.5 397B A17B non-reasoning, per-provider output speed (10k-input workload, 72-h median, snapshot undated; cache-hit data on the page updated 2026-09-26): Nebius FP4 141.4 tok/s, Alibaba Cloud 55.9, Novita 55.7, DeepInfra FP8 41.5, DigitalOcean 13.0; TTFT 1.2-2.2 s. A different cached snapshot showed Nebius 90.7, Alibaba 68.6, Novita 67.9, DeepInfra 35.3 [V/S] — [Artificial Analysis providers](https://artificialanalysis.ai/models/qwen3-5-397b-a17b-non-reasoning/providers)
- Artificial Analysis comparison page: Qwen3.5 397B non-reasoning 56 tok/s, TTFT 2.23 s, end-to-end 11.17 s for 500 tokens [V] — [Artificial Analysis comparison](https://artificialanalysis.ai/models/comparisons/qwen3-5-397b-a17b-non-reasoning-vs-qwen3-5-397b-a17b)

- FrugalGPT (2023): LLM cascades can match best single LLM with up to 98% cost reduction (cost, not latency; 2023 preprint) [P] — [arXiv 2305.05176](https://arxiv.org/abs/2305.05176)
- SGD (above) uses a per-sub-problem difficulty estimate to choose model size [P] — [arXiv 2402.12280](https://arxiv.org/pdf/2402.12280)

### Inferences
- [E] Your measured 25 s for ~1,600 tokens (about 64 tok/s) sits inside the AA band for the same model (56-141 tok/s depending on provider), so SAIA appears to be running typical non-speculative decode speeds. Single-stream per-user speed on Lambda's aggregate benchmark is about 1,269/32 = ~40 tok/s per request under 32-way concurrency, so SAIA load matters.
- [E] Decode speed for mid-size and 3B-active models is higher on average (Qwen3.6-35B-A3B median provider ~90-138 tok/s vs ~56 for Qwen3.5-397B), but the provider spread (10-327 tok/s for the same model) is larger than the model-size effect. Therefore "route to a smaller model" yields maybe 1.3-2x on decode only if SAIA's hardware for that model is faster; benchmark each SAIA model on a fixed 400-token JSON section before deciding.
- [E] RouteLLM-style per-query routers are the wrong tool here: they were trained on chat preferences, optimise cost, and add an inference step. Your pipeline has a known stage/section structure, so static task-to-model routing is simpler and more predictable: e.g. extraction and deterministic-fact verbalisation on a small fast model (qwen3.6-35b-a3b / qwen3-30b-a3b-instruct-2507 / qwen3.8-27b), the interpretive/scientific-synthesis sections on Qwen3.5-397B, critic on Gemma or small model with a verdict-only output. Quality must be gated by an eval on your own gold reports; no published evidence found for scientific report quality by model size.
- [E] Cascades add serial latency when they escalate (draft with small model then redo with big), so for latency they only pay off if escalation is rare; the critic-flag-then-repair loop you already have is a cascade in disguise.
- [E] Concrete output-token cuts: fill identifiers, units, enumerations, citation keys and repeated metadata in code from the deterministic engine; use compact JSON (no indentation/pretty-print whitespace), shortened keys with a post-expansion map, and prose limits per section (paragraph/sentence counts rather than word counts). If 25-45% of the 1,600 tokens are non-prose, the OpenAI rule of thumb implies a 25-45% cut of the 25 s draft, i.e. roughly 6-11 s saved before any parallelism. This is an estimate that depends on your actual schema.

### Gaps
- No SAIA-specific tokens/s measurements are published; AA numbers are for third-party endpoints. DeepSeek V4/V3 and Qwen3.5 speeds on vLLM-on-SAIA hardware are unknown.
- AA pages show internal inconsistencies between snapshots and between table and summary text; treat as order-of-magnitude.
- No latency (as opposed to cost) evaluation of RouteLLM or cascades found.
- No quality evidence for Gemma 4 31B or Qwen3.6-35B-A3B on scientific report sections vs Qwen3.5-397B.

## 5. Speculative decoding (EAGLE-2/3, MTP): what is server-side and what a client can control

### Takeaway
Speculative decoding (EAGLE-3, MTP heads) can give about 1.5-2.5x faster single-stream decode on large models when the server enables it, but gains shrink at high batch sizes and it is purely a server-side configuration; a SAIA client cannot turn it on. The only client-side levers are to ask GWDG whether MTP is enabled for qwen3.5-397b-a17b and to use request patterns that suit it (low concurrency, long outputs).

### Cited Findings
- EAGLE-2 (EMNLP 2024): context-aware dynamic draft tree; arXiv version reports 3.05x-4.26x speed-up across three LLM series and six tasks (20-40% faster than EAGLE-1); ACL Anthology page states up to 5x; lossless (distribution preserved) [P] — [EAGLE-2, arXiv 2406.16858](https://arxiv.org/abs/2406.16858v2); [ACL Anthology](https://preview.aclanthology.org/setup/2024.emnlp-main.422)
- EAGLE-3 (2025): speed-up ratio up to 6.5x, about 1.4x over EAGLE-2, and 1.38x throughput at batch size 64 in SGLang [P] — [EAGLE-3, arXiv 2503.01840](https://arxiv.org/abs/2503.01840)
- vLLM docs warn EAGLE speed-ups in vLLM can be lower than the reference implementation (tracked in vllm issue 9565); an agentic-coding study on Qwen3-8B found EAGLE-3 over 2.5x at batch 1 with gains diminishing rapidly as batch size grows; an older EAGLE-1 measurement in vLLM went from 1.3x at batch 2 to 0.7x at batch 48 [S/P] — [vLLM spec decode docs (v0.8.x)](https://docs.vllm.ai/en/v0.8.5/features/spec_decode.html); [arXiv 2508.08192](https://arxiv.org/html/2508.08192v1)
- Current vLLM docs: speculative decoding targets "medium-to-low QPS, memory-bound workloads"; model-based methods (EAGLE, MTP, draft model, PARD) rated high gain at low QPS, medium-to-high at high QPS; n-gram/suffix decoding gives modest gains; no benchmark numbers on the page [P] — [vLLM speculative decoding](https://docs.vllm.ai/en/latest/features/speculative_decoding/)
- DeepSeek-V3 report: MTP second-token acceptance rate 85-90% across topics, delivering about 1.8x tokens per second; a follow-up paper says 80-90% [P] — [DeepSeek-V3 report, arXiv 2412.19437](https://arxiv.org/pdf/2412.19437); [Insights into DeepSeek-V3, arXiv 2505.09343](https://arxiv.org/pdf/2505.09343)
- Qwen3.5-397B-A17B model card documents MTP serving flags: vLLM `--speculative-config '{"method":"qwen3_next_mtp","num_speculative_tokens":2}'` (SGLang NEXTN variant) [P] — [Qwen3.5 model card](https://huggingface.co/Qwen/Qwen3.5-397B-A17B)
- TokenSpeed on Qwen3.5-397B-A17B-NVFP4 (B200): MTP gives +100% to +159% throughput at batch 1; at high concurrency gains depend on output length (+38% to +90% for outputs over 4,096 tokens at bs 32/64) and fall to near zero or slightly negative for 1,024-token outputs at bs 64 [V] — [PyTorch/TokenSpeed blog](https://pytorch.org/blog/up-to-580tps-new-speed-record-of-qwen3-5-397b-a17b-on-gpu-for-agentic-workloads-with-tokenspeed/)
- Community reports: MTP acceptance above 90% on JSON output for Qwen3.6-27B (vLLM 0.20.x, 2x 2080 Ti, num_speculative_tokens 3, recommended 2); Gemma 4 / Qwen 3.6 MTP up to 3.34x lossless speed-up with 70-85% acceptance on one RTX 6000 PRO; acceptance can fall on domain-specific workloads [S, single community benchmarks] — [search results (Reddit snapshot, aiweekly)](https://aiweekly.co/node/2085)
- OpenAI "Predicted Outputs": client supplies a draft; reported 2-4x faster for code edits, one large file change from about 70 s to about 20 s; benefit scales with overlap; rejected prediction tokens still billed; not available on vLLM-based SAIA (OpenAI/Cerebras feature) [V/S] — [Cerebras predicted outputs docs](https://inference-docs.cerebras.ai/capabilities/predicted-outputs); [secondary summary](https://morphllm.com/openai/predicted-outputs)

### Inferences
- [E] If SAIA ran MTP/EAGLE on Qwen3.5-397B at low load, single-stream decode would be 2x or more of the ~56-64 tok/s observed (TokenSpeed reaches ~580 tok/s on tuned B200 stack, an upper bound that is not comparable). The observed 64 tok/s suggests either no speculation or a shared, batched system; this is only an inference and the way to confirm is to ask GWDG support.
- [E] Client-side behaviours that interact with speculation: lower temperature/greedy-ish sampling raises acceptance (not sourced in this research; widely stated but not verified here); JSON with deterministic fields has high acceptance (community report above); high server concurrency from many users erodes gains. Fan-out of N parallel requests from your client makes server batches larger, which is the regime where speculation helps least, but each of your short section calls is still memory-bound at the server's batch size.
- [E] For repair/patch-like calls where the output largely copies the input, vLLM n-gram/suffix speculation would be the analogue of OpenAI Predicted Outputs; again enabled only server-side. If GWDG can enable n-gram speculation or MTP, the whole-report repair call would benefit most, but targeted repair makes that moot.

## 6. Prefix/prompt caching (vLLM automatic prefix caching)

### Takeaway
APC only shortens prefill (TTFT); for a decode-bound 1,600-token output it saves little, and for hybrid Gated-DeltaNet models such as Qwen3.5 the vLLM prefix-cache hit rate has been reported near zero. Do not plan latency on it; still order prompts static-first for free benefit where it works.

### Cited Findings
- vLLM docs: APC stores KV of earlier queries and reuses shared prefixes; it "only reduces the time of processing the queries" (prefill), so it does not help decode-heavy requests; no downside generally; hybrid Mamba-type models cache state only at block boundaries, with an optional `--enable-mamba-shared-prefix-checkpoint` that has multiple preconditions (EAGLE/MTP on the Mamba group, `--prefix-match-unit`, etc.) [P] — [vLLM APC docs](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)
- Reported effect in a vendor benchmark: mean TTFT 4,343 ms to 970 ms (-78%) with prefix caching on a custom 200-prompt shared-prefix dataset; a 2026 paper (PrefixBench-H100) found scheduling/queueing can outweigh cache hit rate under high concurrency [V/S] — [Jarvislabs vLLM optimisation](https://jarvislabs.ai/blog/vllm-optimization-techniques)
- vLLM issue 36493: Qwen3.5-35B-A3B prefix-cache hit rate 0-0.1% (vs about 20% on Qwen3-30B-A3B with ~20% shared prefix) on vLLM 0.17.0; closed as "not planned" by stale bot on 2026-07-09; a contributor suggested Qwen lacked the Mamba prefix-caching interface [S/P] — [vllm issue 36493](https://github.com/vllm-project/vllm/issues/36493)
- LMCache recipe for Qwen3.5 requires `--mamba-cache-mode align` (GDN does not support the `all` mode); only whole blocks are cached so prompts shorter than one block got 0% hit; MTP reduced hits in one community test; SGLang has a partial solution with extra settings [S] — [LMCache Qwen3.5 recipe](https://docs.lmcache.ai/recipes/qwen3_5.html)
- OpenAI guidance: place dynamic content late in the prompt to maximise shared prefix [V] — [OpenAI latency guide](https://developers.openai.com/api/docs/guides/latency-optimization); input-token reduction yields only about 1-5% latency for a 50% cut [V] (same)
- TokenSpeed (a different engine) implements hybrid prefix caching and reports over 90% KV hit in multi-turn agentic workloads, showing it is an engine-specific capability [V] — [PyTorch/TokenSpeed blog](https://pytorch.org/blog/up-to-580tps-new-speed-record-of-qwen3-5-397b-a17b-on-gpu-for-agentic-workloads-with-tokenspeed/)

### Inferences
- [E] In your pipeline the shared prefix (system prompt, schema, deterministic facts) is probably a few thousand tokens; prefill of that is a small fraction of the 25 s, consistent with OpenAI's 1-5% rule, so even a perfect hit would save well under 1-2 s on Qwen3.5-397B.
- [E] With parallel section calls fired at the same instant, none of them can reuse a prefix that another call is still prefilling, so caching helps fan-out only if a priming call finishes first; not worth the serial delay.
- [E] Gemma 4 31B (critic) architecture was not checked; whether it supports vLLM prefix caching well is unknown.

### Gaps
- Whether SAIA's vLLM version has a working hybrid prefix cache for Qwen3.5; not determinable from public docs (vLLM 0.17.0 issue is the best evidence and it remained unresolved).
- No direct measurement of TTFT vs prompt length for SAIA endpoints.

## 7. Targeted repair vs whole-output regeneration, and prevention over repair

### Takeaway
Regenerate only the failing sections (or emit a patch of failing fields): this converts a ~30 s repair into roughly 3-8 s and removes it from the critical path of passing sections. Published patch results (JSON Whisperer) show -31% tokens at within-5% quality for general document editing, but also warn of missed related updates and array-index errors; section-level regeneration avoids both. Prevention (grammar enums, deterministic validators in the loop, prompts built from rule outputs) should cut the "repair on most enquiries" rate.

### Cited Findings
- JSON Whisperer (arXiv 2510.04717, Oct 2025 v1 preprint): LLM emits RFC 6902 JSON Patch diffs instead of whole documents; with EASE (arrays converted to dictionaries with stable keys) it cuts token usage by 31% while keeping edit quality within 5% of full regeneration; identified problems: LLMs often miss related updates when generating isolated patches and handle array index shifts poorly [P preprint] — [arXiv 2510.04717](https://arxiv.org/abs/2510.04717)
- OpenAI Predicted Outputs: for edits where most output is known, reported 2-4x faster responses; one example from about 70 s to about 20 s; speed-up depends on overlap; rejected tokens still billed [V/S] — [Cerebras docs](https://inference-docs.cerebras.ai/capabilities/predicted-outputs); [secondary summary](https://morphllm.com/openai/predicted-outputs)
- Deterministic client-side JSON repair (jsonrepair/json_repair, OpenRouter "Response Healing") fixes syntax defects without another LLM call; a vendor skill doc claims re-prompting for trivial syntax errors costs 1,000-4,000 tokens and 5-10 s (unverified) [S] — [OpenRouter response healing](https://openrouter.ai/blog/announcements/response-healing-reduce-json-defects-by-80percent/); [safe-json-repair](https://pypi.org/project/safe-json-repair/)
- Tam et al. (2024) also report that using an LLM only to reformat outputs with parse errors makes structured output more reliable without large performance cost [P] — [arXiv 2408.02442](https://arxiv.org/html/2408.02442v1)
- XGrammar paper: constrained decoding moved function-calling structural accuracy from 62% to 100% and XML from 80% to 100%, i.e. structural errors can be removed by construction [P] — [arXiv 2411.15100v3](https://arxiv.org/html/2411.15100v3)
- OpenAI latency guide: run independent steps concurrently; use speculative execution when one outcome is likely (e.g. start the next step assuming the check passes and cancel on failure) [V] — [OpenAI latency guide](https://developers.openai.com/api/docs/guides/latency-optimization)
- No published benchmark found comparing field-level patch repair against full regeneration on latency (search for this returned no direct source) [gap]

### Inferences
- [E] Section-level regeneration is the lowest-risk targeted repair. With sections of ~300-400 tokens, a repair is ~5-8 s sequential per section, and flagged sections can be repaired in parallel (so wall-clock is the slowest flagged section). A field-patch repair (only failing field values, ~50-150 tokens) is ~1.5-3.5 s but needs a stable-keyed schema (the EASE lesson) and a deterministic merge; reserve it for single-field defects such as unit errors, wrong enum values, missing citation IDs.
- [E] Run the cheap deterministic validators first (schema, ranges, required fields, ID existence, numerical consistency against rule outputs; < 0.1 s) and have the LLM critic judge only what code cannot (semantic faithfulness, tone, unsupported claims). The critic then emits a short verdict list (failing section IDs and reasons, tens of tokens) so its 8 s drops mostly to prefill+TTFT, likely 2-4 s (estimate).
- [E] Because repair runs on "most enquiries", the repair rate is a design signal: log which critic findings recur (e.g. missing caveat, wrong units, unsupported claim). Move each recurring class upstream: into the section prompt as explicit rules fed from the deterministic engine, into grammar (enum of allowed evidence IDs, fixed unit strings), or into deterministic post-processing. Target is a repair rate well below 30%, but that number is a goal, not sourced.
- [E] Speculative execution on the repair path: start rendering sections as "checked" only after validation; optionally start the critic for section k as soon as it completes while later sections still stream (pipelining), so the critic's latency is hidden behind drafting except for the last section.
- [E] Cross-section coupling: a fix in one section can invalidate a statement in another; keep a deterministic cross-reference check after each repair and only escalate to a broader regeneration if it trips.

### Gaps
- No published numbers on field-level JSON patch repair latency; JSON Whisperer is a preprint on general editing, not on critic-driven repair.
- No benchmark on how often critic-flagged errors are localised to one section in report-style outputs; must be measured on your own logs.

## 8. Rate-limit-aware parallelism (30 requests/min, 200 requests/hour) and batching

### Takeaway
The hourly cap (200/h = 3.3 requests/min average) is far tighter than the 30/min cap: at 4 calls per report you can serve at most 50 reports/hour, and a 4-way fan-out design at 7-11 calls per report drops that to roughly 18-28 reports/hour. Keep fan-out to 4-5 concurrent calls per report, budget calls per report explicitly, and consider whether the /completions endpoint with a list of prompts is counted as one request (must be tested).

### Cited Findings
- Requester states limits of 30 requests/min and 200/hour [requester-provided]. GWDG's docs show example rate-limit response headers (per-minute 10, per-hour 200, per-day 400, per-month 3000) and say to read the headers of your own responses (`x-ratelimit-limit-*`, `ratelimit-reset`) to check limits; the page states no official quotas [P] — [GWDG SAIA docs](https://docs.hpc.gwdg.de/services/ai-services/saia/index.html)
- SAIA exposes /chat/completions and /completions endpoints (OpenAI-compatible) [P] — [GWDG SAIA docs](https://docs.hpc.gwdg.de/services/ai-services/saia/index.html)
- vLLM's /v1/completions accepts a list of prompts in one HTTP request (one generation stream per prompt, results merged), according to a vLLM forum answer and quoted server code (secondary) [S] — [vLLM forum](https://discuss.vllm.ai/t/llm-memory-caching/2623); [OSV quote of vLLM code](https://osv.dev/vulnerability/PYSEC-2026-3704)
- OpenAI guidance: make fewer requests where steps can be combined (return a JSON object with named fields), but parallelize independent steps; splitting one large request into two sequential smaller ones can reduce latency if a smaller model produces most output but adds a round trip [V] — [OpenAI latency guide](https://developers.openai.com/api/docs/guides/latency-optimization)
- SoT: parallelism may reduce serving throughput under saturated load (more total compute/prefill) [P] — [SoT paper HTML v3](https://arxiv.org/html/2307.15337v3)

### Inferences
- [E] Call budget arithmetic against 200/hour: current design 4 calls/report (extract, draft, critic, repair) gives max 50 reports/hour; "lean" fan-out (1 extraction + 4 section drafts + 1 verdict-only critic + average ~1.5 repair calls) is about 7.5 calls and about 27 reports/hour; "per-section critic" (1 + 4 + 4 + 1.5) is about 10.5 calls and about 19 reports/hour. Per minute, a burst of 5-6 simultaneous calls per report allows about 5 reports/min before the 30/min cap; so with several simultaneous users the hourly counter is the one to watch, not the minute counter.
- [E] Practical rules: (1) a shared client-side token bucket or semaphore tracking both windows, reading `ratelimit-*` headers and honouring `ratelimit-reset`; (2) at most 4-5 concurrent calls per report; (3) prioritise interactive requests over background ones; (4) exponential backoff with jitter on 429, and never fire hedged/duplicate requests (they spend scarce hourly budget); (5) fold cheap steps together (e.g. combine critic for all sections into one call) when the hourly budget is the constraint; (6) consider merging extraction output and section prompts so no step is called twice.
- [E] If SAIA counts requests at the HTTP level, one /completions request carrying N prompts (one per section, chat template applied client-side, same schema constraint) would be one request toward the 30/min and 200/h limits while executing as N parallel generations, but it complicates streaming per section (a single multiplexed stream) and bypasses chat templates and reasoning parsers; this is a hypothesis to test by reading the rate-limit headers before and after such a call.
- [E] The per-day and per-month example headers (400/day, 3000/month) suggest further caps may exist; check the actual headers of the API key in use, since a daily cap of a few hundred requests would bound demo usage more than the hourly cap.
- [E] A client-side result cache keyed on (deterministic-engine inputs, extraction output hash) for repeated enquiries costs no request budget and eliminates latency entirely on a hit; useful for demos and repeated questions.

### Gaps
- Actual enforcement semantics of SAIA's limits unknown (per key vs per user, sliding vs fixed window, whether list-prompt /completions or `n>1` count as one request, whether streaming cancels count).
- Not verified whether the real quotas are the requester's 30/min + 200/h or the docs' example 10/min + 200/h + 400/day + 3000/month.
- No data on queueing under concurrent calls to the same SAIA model.

## 9. Reasoning/thinking toggles (Qwen3-class)

### Takeaway
Qwen3.5 thinks by default, and thinking costs tens of seconds: on Artificial Analysis the reasoning variant needs about 60 s to the first answer token vs 2.2 s non-reasoning (68.95 s vs 11.17 s for a 500-token answer). The toggle is `chat_template_kwargs.enable_thinking=false`; soft switches do not work. For extraction, drafting from grounded facts and JSON filling, non-thinking is the right default; thinking is worth spending only on narrow, hard judgement calls with a token budget.

### Cited Findings
- Qwen3.5-397B-A17B: thinking mode is the default (reasoning inside `<think>` tags); on self-hosted vLLM/SGLang disable with `"chat_template_kwargs": {"enable_thinking": False}` in `extra_body`; the Qwen3 `/think` `/nothink` soft switches are not officially supported; recommended sampling differs: thinking temp 0.6, top_p 0.95, top_k 20, presence_penalty 0.0; non-thinking temp 0.7, top_p 0.8, top_k 20, presence_penalty 1.5; launch with `--reasoning-parser qwen3` [P] — [Qwen3.5 model card](https://huggingface.co/Qwen/Qwen3.5-397B-A17B)
- Artificial Analysis: Qwen3.5 397B reasoning variant: time to first answer token 59.90 s vs 2.23 s non-reasoning; end-to-end for 500 tokens 68.95 s vs 11.17 s; output speed essentially equal (55 vs 56 tok/s). The page also lists 9k reasoning tokens per task [V] — [Artificial Analysis comparison](https://artificialanalysis.ai/models/comparisons/qwen3-5-397b-a17b-non-reasoning-vs-qwen3-5-397b-a17b)
- GWDG docs: "some reasoning models" on SAIA can enable or disable reasoning via the API (links to per-model docs, using Qwen3.6-35B-A3B as an example); model page lists "flexible thinking control" for Qwen3.8-27B without details; recommended Qwen3.5-397B params temp 0.6/top_p 0.95 (identical to Qwen's thinking-mode recommendation) [P] — [GWDG SAIA docs](https://docs.hpc.gwdg.de/services/ai-services/saia/index.html); [GWDG model list](https://docs.hpc.gwdg.de/services/ai-services/chat-ai/models/index.html)
- Practitioner reports: Qwen3.5 needs `enable_thinking` inside `chat_template_kwargs` (top-level flag not enough on some servers); some Qwen3 "Thinking" variants keep reasoning even with the flag false; stripping `<think>` after generation does not save time [S] — [pi issue 2020](https://github.com/earendil-works/pi/issues/2020); [vLLM forum](https://discuss.vllm.ai/t/thinking-token-limit-setting/2400/12); [OpenWhispr issue 512](https://github.com/OpenWhispr/openwhispr/issues/512)
- Runaway reasoning: a Qwen3.5-9B JSON-extraction user found reasoning could consume the whole output budget before JSON appeared; `thinking_token_budget` was silently ignored via `extra_args` on vLLM 0.18.0 [S] — [vLLM forum](https://discuss.vllm.ai/t/thinking-token-budget-silently-ignored-when-passed-via-extra-args-in-vllm-0-18-0/2533)
- Qwen3 technical report: thinking budgets let users trade latency against performance per task [P] — [Qwen3 report, arXiv 2505.09388](https://arxiv.org/html/2505.09388v1)
- Practitioner guidance: for extraction/classification thinking often makes no measurable difference, for multi-step tasks it can be decisive; measure on 50-100 real examples [S] — [Kaitchup](https://kaitchup.substack.com/p/reasoning-budgets-vs-structured-cot)
- "The Format Tax": enabling extended thinking within one generation (separating reasoning from formatting) recovers most format-induced accuracy loss, but this concerns reasoning-benchmark tasks, not grounded report writing [P preprint] — [arXiv 2604.03616](https://arxiv.org/abs/2604.03616)

### Inferences
- [E] The requester's 25 s for ~1,600 tokens suggests thinking is already off (reasoning would add tens of seconds per the AA gap) or is short; it must be verified by inspecting `reasoning`/`reasoning_content` and `usage.completion_tokens` in a draft response. GWDG's recommended temperature 0.6/top_p 0.95 for Qwen3.5 matches the thinking-mode sampling profile, which is a hint (not proof) that SAIA's default may be thinking-on; if so, explicit `enable_thinking: false` via `extra_body.chat_template_kwargs` could be the biggest single win (tens of seconds), and the Qwen non-thinking sampling profile (temp 0.7, top_p 0.8, presence_penalty 1.5) should be used with it.
- [E] Where thinking may pay for itself: the critic's semantic-faithfulness judgement for flagged sections, or a single high-stakes interpretation section, with a bounded budget (and a fallback if the budget is not honoured). Everywhere else (extraction, grounded drafting from deterministic facts, section verbalisation) use non-thinking with schema field order evidence-then-conclusion as lightweight "speak first".
- [E] A thinking critic would add the thinking time in series; if you use one, run it asynchronously after first display and show a "verifying" badge.

### Gaps
- No controlled benchmark found of Qwen3.5 thinking on vs off for structured scientific report quality.
- Whether SAIA's gateway forwards `chat_template_kwargs` for qwen3.5-397b-a17b is not documented on the pages I could read; GWDG's per-model page was not reachable.
- Gemma 4 31B thinking-mode behaviour and latency on SAIA not covered.

## 10. Quantified menu of techniques and recommended latency budget/design (synthesis for this case)

### Takeaway
The combination of (1) verifying/disabling thinking, (2) filling deterministic fields in code and shrinking the JSON, (3) deterministic-skeleton parallel section generation with per-section streaming, (4) deterministic-validators-first plus verdict-only critic, and (5) section-targeted repair should move a typical report from 40-72 s to roughly 14-25 s total (about 14-18 s when no repair is needed), with deterministic content on screen in under 0.5 s and first streamed LLM text around 5-7 s. These are estimates built from the cited rules of thumb; none was measured on SAIA, so every row needs a one-day benchmark.

### Cited Findings
- Cost model for decode-bound work: output tokens dominate latency, about linear, while input tokens matter little (OpenAI rules of thumb: -50% output ~ -50% latency; -50% input ~ -1-5%) [V] — [OpenAI latency guide](https://developers.openai.com/api/docs/guides/latency-optimization)
- Observed ceilings and floors for Qwen3.5-397B decode: roughly 13-141 tok/s across hosted providers (AA), about 64 tok/s implied by the requester's draft stage, up to about 580 tok/s on a tuned B200 stack with MTP [V] — [Artificial Analysis](https://artificialanalysis.ai/models/qwen3-5-397b-a17b-non-reasoning/providers); [PyTorch/TokenSpeed](https://pytorch.org/blog/up-to-580tps-new-speed-record-of-qwen3-5-397b-a17b-on-gpu-for-agentic-workloads-with-tokenspeed/)
- UX targets: 1 s uninterrupted flow, 10 s attention limit with progress indicator beyond [P/V] — [NN/g](https://www.nngroup.com/articles/response-times-3-important-limits/)
